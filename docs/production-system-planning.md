# 生産システム計画の定義

`production-system-planning@1.0.0` は、工場の生産ラインを、製品と量の要件から、作業・設備・バッファ・搬送・作業者・配置として計画し、そのラインを時刻で動くモデルにして流して確かめ、改善の案を比べて採り、承認を経て関係者に説明できる形にする汎用定義です。題材・手法・道具・出力形式は固定しません。既存の format 1 の schema を使います。

**11工程・11成果物・14項目・29引用／網羅規則・33達成条件**。各工程に人が確かめる達成条件があります。AI の達成条件は、見出しと項目の抜け、出典と確からしさの記入、繰り返しとばらつきの記入、引用と網羅に限ります。案の良し悪し、モデルが現実を表しているか、制御と配置の安全を AI の合格だけで決めません。

## セクションと工程

| セクション | 工程 | 主な成果物 |
|---|---|---|
| 企画 | 進め方 → 生産の要件 | 進め方、生産の要件 |
| 計画 | 工程の設計 → ラインの設計 → 入力のデータ・配置の計画（並行） | 工程の設計、ラインのモデル、入力のデータ、配置の計画 |
| 検証 | モデルの妥当性の確認 → 実験と比較・制御の確認（並行） | モデルの妥当性の確認、実験の記録、制御の確認 |
| 判断と伝達 | 計画の承認 → 説明と記録 | 計画の承認、説明と記録 |

`after` は工程の**受け入れ順**です。実験で採った案は、ラインのモデルや配置の新しい版になります。そのときは影響する妥当性・実験・制御・配置の確認をやり直し、承認は最後の版に対して行います。循環する工程は定義しません。

## 使い方と省略

対象と出口を「進め方」に書きます。設備の制御をモデルにつながない、新しい建屋で配置の制約が無い、品種が一つで作業が少ない、などの場合は、工程を省く理由と代わりの確認を書きます。モデルの妥当性の確認は、実績の無い新しいラインでも、手計算や極端な条件との比べで行い、省きません。

題材が実在の工場・製品のときは、公開された情報から作った近似であること、その持ち主とは関係が無いことを「進め方」と「説明と記録」に書きます。参考にした手法（離散事象のシミュレーションなど）は一般の言葉で書き、特定の製品の名前・画面・用語・見本のモデルを写しません。

人と AI が一緒に計画するときは、AI に任せる作業（モデルの組み立て、データの当てはめ、実験の実行、事項の一覧化など）と、人が決めること（要件、案の採否、データの仮定の受け入れ、承認）を「進め方」に書きます。

## 項目と引用

| 項目 | ID | 置く成果物 |
|---|---|---|
| 要件 | RQ-{nn} | 生産の要件 |
| 製品の種類 | PT-{nn} | 工程の設計 |
| 作業 | OP-{nnn} | 工程の設計 |
| 資源 | RS-{nnn} | ラインのモデル |
| つながり | CN-{nnn} | ラインのモデル |
| データ | DS-{nn} | 入力のデータ |
| 区画と通路 | ZN-{nn} | 配置の計画 |
| 配置の事項 | LI-{nn} | 配置の計画 |
| 妥当性の確認 | VC-{nn} | モデルの妥当性の確認 |
| 案 | SC-{nn} | 実験の記録 |
| 所見 | FD-{nnn} | 実験の記録 |
| 制御の確認 | CC-{nn} | 制御の確認 |
| 判断 | DC-{nn} | 計画の承認 |
| 説明の場面 | PS-{nn} | 説明と記録 |

資源は、投入口・設備・並列の設備・組立・バッファ・コンベヤ・搬送車・作業者・出口などを、欄 `kind` で分けて一つの種類にします。つながりは欄 `from`・`to` に資源の ID を持ち、ラインのモデルを図（資源が点、つながりが線）で見せます。

主な引用は、**製品の種類 → 要件、作業 → 製品の種類（と先行の作業）、資源 → 受け持つ作業、つながり → 資源、データ → 資源か作業、配置の事項 → 区画か資源、妥当性の確認 → 資源・データ・要件、案 → 変えた資源・データ・つながり・区画、所見 → 案（と要件・資源）、制御の確認 → 資源、判断 → 所見・配置の事項・妥当性の確認・制御の確認、説明の場面 → 案・判断・所見**です。

網羅では、すべての製品の種類に作業があること、すべての作業を資源が受け持つこと、すべての案に所見があること、すべての所見・配置の事項・制御の確認に判断があることを確かめます。要件・流れの外の資源（作業者・搬送車など）・時間のデータの要らない資源（バッファ・出口など）・妥当性の確認・説明しない案は、理由を書けば `exempt` で除けます。実験の記録では、所見と要件をマトリクスで見て、どの要件に答えた所見かを確かめられます。

## 実験で確かめること

乱数を使うモデルの結果は、1 回の実行では決めません。実験の記録には次を書きます。

- モデルと入力のデータの版、流した時間、慣らしの時間（始めの空の状態を除く時間）。
- 繰り返しの数と乱数の種。所見の値は平均とばらつき（信頼区間など）で書く。
- 案どうしは、同じ時間・同じ慣らし・同じ繰り返しの数で比べる。
- 生産数・稼働の内訳（加工・待ち・詰まり・故障・段取り・休み）・ボトルネック・仕掛り・リードタイムのうち、要件に効くもの。

ボトルネックの決め方（稼働率、詰まりと待ちの割合、稼働が続く時間の長さなど）は利用側が決め、実験の条件に書きます。映像は人が見て、数字で拾えない不自然さ（物が重なる、搬送車が抜ける、作業者が持ち場にいない）を確かめます。

## 評価と承認の境界

- AI は見出しと項目の抜け、出典の無い要件とデータ、繰り返しとばらつきの書き漏れ、引用と網羅の切れ、処置の無い事項を指摘します。実験の結果は、モデルとデータが扱った範囲の結果として扱います。
- 人は要件・データの仮定・モデルの妥当さ・案の採否・承認を決めます。制御と配置は、それぞれの責任者が確かめます。
- 定義の検査が通っても、実際のラインの生産数・安全・法令への適合を保証しません。

## 利用側が受け持つこと

- **モデルと計算**：資源とつながりを持つモデル、時刻を進める計算（離散事象など）、乱数の種の扱い、稼働の内訳と生産数の統計。
- **実験**：繰り返しとパラメータの振り分け、ばらつきの計算、結果の表の書き出し、その速さ。
- **配置と3D**：建屋のモデルの上に資源を置く道具、干渉の検査、時刻を追う再生と映像。
- **制御**：設備と搬送の制御のプログラムを、モデルのセンサーと動作につなぐ道具。

## 検証

`npm run check` が正式な必須検査です（schema の生成物の整合、定義の検査、契約試験、見本の検査）。見本 `fixtures/production-system-planning/small-line.json` は、架空の小さな組立ラインで項目と引用の形を示します。定義の検査は計画の出来や完成を保証しません。
