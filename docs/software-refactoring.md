# ソフトウェアのリファクタリング

[定義](../definitions/software-refactoring.json) は、既に存在するソフトウェアの設計と実装を見直すための独立した進め方です。初めて製品を作る流れとは分け、今使われるコード・契約・試験・版を入力にして、重複、不要な互換、複雑な依存、古い検証、保守上の負担を改善します。

## いつ使うか

- 複数の機能や層をまたぐ責務の整理、依存方向の見直し、使われない処理・互換や試験の終了
- 保存や承認など複数の経路にまたがる共通処理への整理
- 検証・配布の単位や開発時の待ち時間の見直し、独立した部品やリポジトリへの分離判断

機能実装中の小さい関数抽出・命名変更・局所的な重複解消は、通常の開発工程で行えます。緊急の不具合修正は大きな構造変更の完了待ちにせず、影響範囲を絞って直してください。既存製品の調査と構造の改善をまとまった仕事として扱う場合に、この定義を使います。

## 工程と成果物

| 工程 | 成果物 | 主な判断 |
| --- | --- | --- |
| 現状と対象 | 調査基準と限界の記録、現状と指摘の台帳 | 対象の固定版、実際に使われる経路、観測と推定、保留 |
| 守る契約と意図する変更 | 維持と変更の契約表 | 維持する動作と、不具合修正など意図的に変える動作 |
| 改修設計と実施順 | 変更単位と実施計画、改修後の構成と依存図、構成変更の設計判断 | 責務、依存方向、変更単位、削除範囲、安全な順番 |
| 改修と不要な経路の終了 | 改修したソースコード、改修の変更記録 | 実装・削除、現在の試験への付け直し、作業の保護 |
| 回帰と改善効果の確認 | 検証と契約の対応表、改善効果の測定表、改善の評価と副作用 | 維持・変更した契約の検証、改善の実測、未実施・失敗 |
| 受入と正本への反映 | 受入と反映の記録 | 元の製品への反映、残件、受入・保留・やり直し |

工程は **調べて決める → 設計して直す → 確かめて受け入れる** の3つのまとまりにしています。各工程に、人が成果物を確認する達成条件があります。

## 項目・引用・網羅

| IDの形 | 項目 | 内容 |
| --- | --- | --- |
| `BL-{nn}` | 基準 | 固定した版と範囲、参照可能な根拠 |
| `FD-{nnn}` | 指摘 | 問題・影響・優先度・確認の確かさ |
| `CT-{nnn}` | 契約 | 維持する動作／承認して変える動作と検証方法 |
| `RF-{nnn}` | 変更単位 | 対応する指摘・契約・設計・作業順 |
| `CP-{nnn}` | 構成要素 | 改修後の責務、入出力、境界 |
| `DP-{nnn}` | 依存 | 構成要素間の参照方向と目的 |
| `VE-{nnn}` | 検証 | 確認した変更・契約・対象版・結果 |
| `ME-{nn}` | 改善の測定 | 変更前後を比較した指標と測定条件 |
| `RS-{nn}` | 残件 | 持ち越す課題と担当・理由 |

`FD → BL`、`CT → BL`、`RF → FD/CT`、`CP → RF`（任意）、`DP → CT`（任意）、`VE → RF/CT`、`ME → RF` の引用を定義しています。構成図の項目 `CP-{nnn}`（構成要素）と `DP-{nnn}`（依存）は、改修後の責務と依存方向を示します。契約と変更単位は、検証によって網羅される必要があります。指摘は、変更単位で対応するか、除く理由を示します。各変更の改善測定ができないときも、理由を残します。

**引用の向きは、下流の項目から根拠となる上流の項目へ向けます。** 下流への影響は、この引用を逆にたどって調べます。指摘・契約・変更・検証の対応を、文書の文章だけから推測させません。

### 構成図と変更計画の引用

`dependency-map` は `uses` で `change-plan` をもとにするため、構成要素CPが変更単位RFを引用します。例えば、構成要素 `CP-001` を変更単位 `RF-001` のために改修するとき、引用表に次の組を記録します。

```json
{ "from": "CP-001", "to": "RF-001" }
```

`component-cites-change` の `min: 0` は、背景として図に載せる構成要素にも一律に引用を要求しないためのものです。改修対象の構成要素では、対応する変更単位への引用を実際に記録します。規則を宣言するだけで引用が生成されたり、未接続の判定が消えたりするわけではありません。「改修対象」欄にRFの名前を書くだけでも引用の代わりにはなりません。

この組について、PaoBubの未接続判定は引用なし・逆向きの `RF-001 → CP-001` では未接続、`CP-001 → RF-001` を記録すると接続ありになります。これは構成要素と変更単位の根拠関係であり、図の依存項目DPが持つ構成要素間の `from` / `to` とは別です。

同じように、`dependency-map` は `uses` で `contract-ledger` も使うため、契約に関わる依存DPは契約CTを引用します（`dependency-cites-contract`、`min: 0`）。例えば依存 `DP-002` が契約 `CT-003` の保存の保証を通すとき、`{ "from": "DP-002", "to": "CT-003" }` を記録します。契約に関わらない依存には引用を求めません。

## PaoBubで保存できる成果物の分け方

表・カンバン・マトリクス・構成図は、各項目の種類に対応する JSON 配列として保存します。見出しに項目がない自由記述はこの JSON 配列の表示・保存対象外になるため、**意図・比較条件・設計判断・変更記録・受入判断は独立した文書成果物として保存**します。

- **調査:** `baseline-note` はMarkdown文書（固定版と調査限界）、`inventory-report` は指摘の表。
- **契約:** `contract-ledger` は契約ごとに境界・対象外の欄を持つ表。
- **設計:** `change-plan` は変更単位のカンバン＋表、`dependency-map` は構成要素と依存の図、`design-review` は変更前後の比較・削除判断・切り戻しの文書。
- **実装:** `code-refactor` はソースコード、`implementation-record` は実装・撤去・局所検査の記録。
- **検証:** `verification-ledger` は引用マトリクス＋検証表、`improvement-report` は改善指標の表、`improvement-assessment` は比較条件と副作用の評価文書。
- **受入:** `completion-record` は残件（RS）と正本への反映・人の判断を共に残す文書。

表の列名、カンバンのカードの欄名、構成図の `from` / `to` は、各 `outline.describe` に同じ文字列を明示します。検証台帳には「結果」の合否だけでなく、再現条件・異常系・未実施理由と人の受入を要求します。

現行のPaoBubは `form: "コード"` の成果物を、そのIDが `code` で始まる場合は `src/`、それ以外は `tests/` に初期配置します。この定義は `code-refactor` として配置の取り違えを避けます。**これは定義に依存する本来の配置規則ではなく、利用側の現在の実装制約への対処**です。長期的にはProjectごとの明示的な保存場所の指定が望まれます。

なおPaoBubのマトリクス表示は現状、引用関係の**閲覧**を提供します。マトリクスのマスを操作して引用を増減する機能はこの変更の範囲外で、引用は対応するデータ・操作で管理します。

## 変更前後の扱い

1. 最初に調査対象の版と入力データを固定します。実行していない試験を「通った」とせず、静的解析での推定と再現した不具合を分けます。
2. 契約を「維持」と「意図的に変更」に分けます。後者には理由・新しい期待・確認者を記載し、現在の不具合を守る契約にしません。
3. コード・試験の撤去前に、現在の利用経路・公開契約・未保存作業・データを確かめます。古い互換を残すことも、旧版と同じ出力を再現することも、それ自体を達成目標にしません。
4. 仕様の対象・引用・認可・版・承認・監査などが関係する場合は、失敗・競合・再送・失効を含む肯定・否定の経路を検証します。
5. 改善効果は、行数やテスト削除数だけではなく、依存関係、試験・ビルド時間、変更の影響範囲などの目的に合う指標で確かめます。比較条件が違う場合はその限界を書きます。
6. 確認後、元の製品で正本となる仕様、構成、試験対応、運用の記録へ結果を反映します。未完了の作業は残件にします。

## 既存の製品開発との関係

`software-product` は製品を企画・設計・実装・公開する定義で、`software-refactoring` は既存製品の品質と変更容易性を改善する独立定義です。元の製品の固定版や検証結果は参照しますが、仕様本文を複製して第二の正本にしません。

現行の定義形式（format 1）の `after` と `uses` は**同じ定義内の工程・成果物**を指します。異なる定義を一つの工程に埋め込んだり、同じProjectへ自動的に差し込む機能を、この追加は要求・実装しません。利用する側は必要な既存製品の版と受入記録を参照して開始し、結果を元の製品へ反映してください。

## 検査

```sh
npm ci
npm run check
```

新しい定義は既存のschemaと共通 `check(definition)` で検証します。Schemaや検査器を複製・変更する必要はありません。
