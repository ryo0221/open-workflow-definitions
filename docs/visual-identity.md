# ビジュアル・アイデンティティ制作の定義

`visual-identity@1.0.0` は、ロゴ・シンボル・アプリアイコン等を、ブランド理解から探索、試作、比較、採用、マスター制作、用途別展開、引き渡しまで進める汎用定義です。特定企業や製品、Editor、画像生成手段、出力形式を固定しません。既存の format 1 の schema を使用します。

**14工程・15成果物・15項目・30引用／網羅規則・29達成条件**。各工程には人が確認する達成条件があります。AIの達成条件は項目の引用・網羅、版と証跡、決まった見出し・レイヤー・検証条件の不足確認などに限り、デザインの美しさ、ブランドらしさ、権利上の問題がないことを自動判定しません。

## セクションと工程

| セクション | 工程 | 主な成果物 |
|---|---|---|
| 企画 | 進め方 → ブランド理解 → 用途と要件 | 進め方、ブランドブリーフ、用途と要件 |
| 探索 | 調査と参考収集 → 表現コンセプト → 造形探索・ラフ | 参考資料、デザイン方針、ラフ |
| 造形 | 候補制作 → デザイン詳細化 | デザイン候補、造形とレイヤーの設計 |
| 評価と判断 | 比較評価 → 使用環境での検証 → 採用判断 | 候補評価、環境検証、採用判断 |
| 完成と展開 | マスター制作 → 展開と利用ルール → 引き渡しと学び | マスター、展開版、利用ガイド、引き渡し記録 |

`after` は工程の**受け入れ順**です。初期ラフや試作を前倒ししてよいものの、未承認の上流工程を承認済み扱いにしません。修正は成果物の新版として記録し、影響のある評価・検証・承認を利用側で再確認します。循環する工程は定義しません。

## 使い方と省略

制作対象と出口を「進め方」に記します。企業のロゴ、製品のシンボル、単体のアプリアイコンでは、必要な用途と展開版が異なります。不要な派生版を無理に作らず、範囲外にした理由と代替確認を記します。1候補しか作らない場合も、比較探索を省略する理由を残します。ロゴタイプや字体を用いない制作では、その仕様欄を該当なしとします。

人とAIが協働する場合、ラフ・レイヤー・パーツごとにどちらが生成・修正・採用したかと、AIに渡してよい資料の範囲を記録します。デザインの採否と権利・商標の確認をAIの自動合格だけで確定させません。

## ロゴ・シンボル・アプリアイコン

- **ロゴ**：文字とシンボルの組み合わせ、比率、書体、余白、単色版、縦横の配置などを用途に応じて扱います。
- **シンボル**：文字なしでも識別できる造形、背景との関係、形の不変部分を設計します。
- **アプリアイコン**：小サイズでの視認性、背景、切り抜き、ライト／ダーク、端末等の表示条件を用途と要件で定め、検証に残します。
- **ブランドキャラクター等**：必要なら同じ工程で題材を定義します。ただし動き・物語・追加の制作工程は別定義に任せます。

アプリアイコン固有の機種・配布先の規格や、編集・書き出し可能な形式はこの定義に固定しません。利用側が用途の要件として定め、Editor Platformのcapabilitiesと照合します。

## 項目と引用

| 項目 | ID | 置く成果物 |
|---|---|---|
| ブランド特性 | BA-{nn} | ブランドブリーフ |
| 用途 | UC-{nn} | 用途と要件 |
| デザイン要件 | RQ-{nn} | 用途と要件 |
| 参考資料 | RF-{nn} | 調査と参考資料 |
| デザイン原則 | DP-{nn} | デザイン方針とコンセプト |
| 表現コンセプト | CP-{nn} | デザイン方針とコンセプト |
| ラフ | SK-{nnn} | ラフと造形探索 |
| デザイン候補 | CA-{nnn} | デザイン候補 |
| 編集レイヤー | LY-{nnn} | 造形とレイヤーの設計 |
| 候補評価 | EV-{nnn} | 候補の比較評価 |
| 環境検証 | VT-{nnn} | 使用環境での検証 |
| 採用判断 | SL-{nn} | 採用の判断 |
| マスター | MA-{nn} | デザインのマスター |
| 展開版 | VA-{nnn} | 展開版の一覧 |
| 学び | LE-{nn} | 引き渡しと学び |

主要な引用は、**デザイン原則 → ブランド特性、コンセプト → 原則、ラフ → コンセプト、候補 → ラフ・要件、レイヤー → 候補、評価 → 候補・原則・確認したレイヤー、検証 → 候補・要件・確認したレイヤー、採用判断 → 候補・評価・検証、マスター → 採用判断、展開版 → マスター・用途、学び → 判断などの根拠**。参考資料への引用は任意です。

網羅確認では、ブランド特性を原則が、用途を要件と展開版が、要件を検証が、コンセプトをラフが、候補を評価が、レイヤーを評価と検証が、マスターを展開版が扱っているか確認します。不要な項目は理由つきの `exempt` を許します。用途にマスターをそのまま使う場合も、その用途に対応する展開版の項目を持ち、元マスターを引用して「変更なし」と記します。単なる説明文だけで用途を充足したことにはしません。

**採用判断の版と要件の網羅**は全体の `requirement-covered` や参照の存在だけでは確定しません。採用対象の **候補 × 固定版 × 適用要件** ごとに、同一候補・同一固定版の検証結果が存在するか確認します。別候補・別版の検証を流用してはいけません。未検証・不合格・適用除外を区別し、例外として採用する場合は各要件の根拠・残余リスク・責任者の明示判断を残します。候補・評価・検証・レイヤーが同じ固定版の構成に属すること、採用したマスターがその決定版を引き継ぐことはHostが実体・版を照合し、人が承認します。

**反例（採用判断で不合格にする例）**：候補AとBの双方に要件RQ-01・RQ-02が適用され、Aの固定版v1についてRQ-01のみ、Bの固定版v1についてRQ-02のみ検証された場合、全体の `requirement-covered` が成立しても候補Aを通常採用してはなりません。A v1 × RQ-02 は未検証です。例外採用するならA v1に対する未検証と責任者の判断を明示します。

**レイヤー変更の伝播**：LY-001の配色・形状・構造を変更した場合、評価・検証が確認したLY-001の版を直接引用することで、LY-001 → 評価／検証 → 採用判断 → マスター → 展開版の影響経路を成立させます。各評価・検証は対象候補の固定版に属する確認レイヤーを引用し、レイヤー単位の引用漏れや別版の混入をHostが確認します。候補全体の新版への更新だけに依存しません。レイヤーを参照しないことに正当な理由がある場合は `exempt` に理由を残し、その例外を人が承認します。

## 評価と承認の境界

- AIは項目・参照・必要な検証・レイヤー構成など、決めた条件の抜けを指摘します。画面や原本を読み取れない場合には未確認とします。
- 人はブランドとの整合、美的判断、候補の採否、使用感、ライセンス・類似商標に関する最終判断を行います。専門家の調査が必要な権利問題を未確認のまま適法と断定しません。
- 採用しなかった案や未完の検証結果も来歴に残せますが、成果物として受け入れた版と取り違えないようにします。

## 利用側が受け持つこと

- **Editorと成果物の実体**：ラフ、ベクター、画像、レイヤー、文字、マスター等を編集し、保存・再読込・出力できるEditorの選定と機能検証。
- **実体と項目の対応**：候補・レイヤー・原本・派生版を管理対象の実体と固定した版に対応付けること。内部IDを配布物の中に埋め込まないこと。
- **AIの来歴と権限**：生成依頼、参照資料、操作、承認、採否、外部への送信・利用許可を保持すること。
- **改訂と再評価**：ラフと候補を繰り返す単位、LY等の項目変更から引用をたどる影響分析、採用後にレイヤーや要件が変更された場合の評価・検証・承認の再確認。同じ候補・固定版に属する適用要件とレイヤーの突き合わせをHostが実行し、全体網羅の成立のみで採用を許さない。
- **実サイズと権利の検証**：媒体固有の表示仕様、視認性、商標・ライセンス・フォント等の実際の確認。

## 検証

`npm run check` が正式な必須検査です（schemaの生成物整合、定義検査、契約試験）。`node scripts/check.mjs` のみでは全検査の代わりになりません。定義の検査は制作物の完成や審美的評価を保証しません。
