# workflow-definitions

任意の分野のワークフローを、工程・成果物・項目の種類・達成条件と、それらの関係として定義するためのリポジトリです。

本リポジトリは、ワークフローの定義、データ形式、および定義の基本検査を提供します。
AI による作業実行、案件ごとの変更管理、承認管理、成果物の品質保証を自動実行するエンジンは含みません。
定義は発展途上であり、採用する版を固定して利用してください。

## 置いてあるもの

| 場所 | 中身 |
|---|---|
| `definitions/<id>.json` | 定義の本体。定義ごとに 1 ファイル |
| `schema/definition.schema.json` | 定義の形（JSON Schema） |
| `scripts/check.mjs` | 形と参照の検査 |
| `CHANGELOG.md` | 版ごとの変更の記録 |
| `LICENSE` | 定義・Schema・検査スクリプト・文書に適用する MIT ライセンス |

## 利用方法

個々のワークフローは、共通のデータ形式で `definitions/<id>.json` に定義します。
現在は、ソフトウェア開発向けの定義例として `definitions/software-product.json` の **`software-product@1.5.0`** を収録しています。
利用する定義ファイルと `schema/definition.schema.json` を Claude に添付するか、独自ツールから JSON として読み込んで利用できます。
Claude には、例えば「添付した定義の工程・成果物・達成条件に沿って作業を進め、判断が必要な箇所を人に確認してください」と伝えます。
どちらの使い方でも、案件ごとの成果物・引用・試験の対応・証拠・承認は、利用者側で管理し、必要な試験と人による確認を行ってください。
定義を渡すことや基本検査に通ることだけで、成果物の品質が自動的に保証されるわけではありません。

`software-product` では、引用・網羅や試験と受入条件の対応を求める規則も、公開する定義の一部です。
その中の `test-trace` は試験と受入条件の対応表を作るための規約であり、案件の対応表そのものを収録したデータではありません。
案件ごとの対応表・証拠・承認の台帳や、作業を実行・評価・最適化する内部実装は含みません。

利用時には定義の `id` と `version` に加え、取得したリポジトリの commit SHA、または保存した配布ファイルのチェックサムを記録してください。
`main` の最新版へ自動追従せず、固定した版を継続して使い、更新時に差分を確認してください。
`CHANGELOG.md` にある過去版の記録は、過去版のファイルやタグがその配布元で公開されていることを意味しません。

## 定義の書き方の原則

- **今の規範だけを書く。** 変更の経緯・理由・由来・過去の版は定義に書かず、`CHANGELOG.md` に書く。
- **道具に依らない。** 製品・サービス・道具の名前、ファイル名やパスを書かない。役割の言葉で書く。
- **関係は明示の欄で書く。** 工程の順・成果物・達成条件のつながりは、ID の参照で書く。文章から関係を読み取らせない。
- **版は Git で管理する。** 版ごとにファイルを分けない。定義の `version` は、変更のたびに上げてタグを付ける。

## 定義の形

```
定義
├─ phases        工程。順（after）・目的・作る成果物・達成条件
├─ deliverables  成果物。形（文書・表・図・画面・コード）と、見出しの並び（outline）
├─ items         ID を持つ項目の種類と、ID の形
├─ rules         引用の規則（cites）と網羅の規則（covered）
└─ acceptance    達成条件。誰が確かめるか（人・AI）と、機械で確かめる規則
```

形の詳細は `schema/definition.schema.json` を見てください。

## 項目と引用

成果物の中の一つ一つ（ストーリー・受入条件・画面・遷移など）は、ID を持つ項目になる。見出しの `item` が、その見出しの下の一つ一つをどの種類の項目にするかを決める。

定義を使う道具は、次のことを守る。

- **ID は変えず、使い回さない。** 項目を消しても、その ID は別の項目に付けない。
- **引用は本文の外の表で持つ。** 引用（どの項目がどの項目をもとにしているか）は、成果物の本文やコードに書かず、項目の ID の組を並べた引用の表に持つ。表は表としても図としても見せられる。文章の中の言及から引用を読み取らない。
- **影響は引用だけで決める。** 上流の項目が変わったら、その項目を引用している下流の項目を、引用をたどって全部出す。同じ版の組み合わせなら、いつも同じ結果になる。
- **項目の変化は中身で比べる。** 版の前後で中身が変わった項目だけを「変わった」とする。
- **網羅の規則で除くときは理由を書く。** `exempt` のある規則だけ、理由を書いた項目を除ける。

## 検査

Node.js 24 で動作確認しています（検証時: v24.19.0）。追加パッケージのインストールは不要です。
ファイル一式を取得・展開し、`package.json` があるディレクトリで実行してください。

```sh
node scripts/check.mjs
```

`npm run check` でも同じ検査を実行できます。
検査の実行にネットワーク接続、非公開リポジトリの認証、環境変数は必要ありません。

ID の重なり、存在しない参照、工程の順の循環、成果物や達成条件の無い工程などを見つけます。
検査対象は定義ファイルの構造と参照です。JSON Schema の全制約を検証する汎用バリデータではありません。
案件の成果物や試験結果を読み込んで、達成条件の充足や人の承認を判定するものではありません。
